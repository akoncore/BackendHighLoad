# Протоколы и связь с SIS 1

## Решение

Для SIS 2 реализованы REST/JSON и gRPC/Protobuf с общей бизнес-логикой.
REST проще вызвать вручную. gRPC даёт строгий контракт и компактные сообщения.
Предпочтение по скорости определяется измерением, а не названием протокола.

Официальные пояснения: [gRPC deadlines](https://grpc.io/docs/guides/deadlines/),
[gRPC retry](https://grpc.io/docs/guides/retry/).

## Сравнение

| Свойство | REST | gRPC |
|---|---|---|
| Формат | JSON | Protobuf |
| Транспорт в benchmark | HTTP/1.1 | HTTP/2 |
| Вызов | HTTP-метод и URL | Метод из proto |
| Цена | decimal string | decimal string |
| Версия при изменении | If-Match: "1" | version=1 |
| Ключ создания | Idempotency-Key | idempotency_key |
| Пустой следующий курсор | null | пустая строка |
| Тайм-аут клиента | общий бюджет 2 с в RestClient | withDeadlineAfter |
| Повторы | до 3 попыток: 503/ошибка соединения | до 3 попыток: UNAVAILABLE |

Класс GrpcClients задаёт retry для GetProduct, ListProducts и CreateProduct.
Deadline нужно задать на stub при каждом логическом вызове: он покрывает повторы.
Встроенный gRPC retry использует backoff с jitter. RestClient использует
100/200 мс и учитывает целочисленный Retry-After. 400/404/412/422 не повторяются.
PUT/DELETE в эти retry-клиенты не включены.
Benchmark использует отдельные клиенты без повторов.

## Ошибки

| Причина | HTTP | gRPC |
|---|---|---|
| Неверные поля, UUID или параметры | 400 | INVALID_ARGUMENT |
| Товар не найден | 404 | NOT_FOUND |
| Тот же ключ, другие данные | 422 | INVALID_ARGUMENT |
| Устаревшая версия | 412 | ABORTED |
| Отсутствует If-Match | 428 | —; version в gRPC обязательна по смыслу |
| version=0 в gRPC | — | INVALID_ARGUMENT |
| Ошибка доступа к БД | 503 + Retry-After | UNAVAILABLE |
| Истёк срок ожидания клиента | HttpTimeoutException | DEADLINE_EXCEEDED |

JSON ошибки: `{"error":{"code":"not_found","message":"Товар не найден"}}`.
Транспортные ошибки REST-клиента не являются HTTP-ответом сервера.

## Что перенесено из SIS 1

Источник: [OpenAPI SIS 1](https://github.com/akoncore/BackendHighLoad/blob/ffc861f5b2b459b08ed187bf1388dfd3dfdb9619/product-catalog-design/api/openapi.yaml).

Сохранены пути CRUD, UUID, price как строка, currency, category_id, stock,
version от 1, updated_at, ETag/If-Match, ответ 201 при повторном создании,
422 при другом теле с тем же ключом и структура error.

В присланном упрощённом примере отсутствовали currency и category_id.
Здесь они обязательны, как в исходном ProductInput SIS 1.
stock можно не указывать: используется 0.

## Осознанные сокращения

Это **не полная реализация OpenAPI SIS 1**:

- Нет description, brand_id, attributes и image_urls. Неизвестные JSON-поля
  отклоняются, чтобы данные не терялись молча.
- Нет JWT, ролей, CDN, rate limiting, поиска, категорий и изображений.
- category_id — положительное число; существование категории не проверяется.
- Общий GET /products добавлен для SIS 2. Порядок — лексикографический id,
  курсор — URL-safe Base64 от последнего id, limit 1–100, по умолчанию 20.
- Вместо 409 при незавершённом повторном POST используется ожидание транзакции.
  При успешном завершении первого запроса второй получает 201 с исходным телом.
- Данные хранятся в отдельной сокращённой схеме; миграция всей схемы SIS 1 не сделана.
- Для прозрачности учебного кода выбраны JDBC и явный SQL вместо JPA.
- Нет автоматического удаления старых ключей: исходный ответ хранится бессрочно.
  Для реального сервиса нужна согласованная политика срока хранения.
- Ключ глобален в учебной базе. При добавлении авторизации его нужно связывать
  с владельцем операции.
- price принимает обычную десятичную запись без экспоненты: до 17 цифр,
  до 2 знаков после точки. Название обрезается по краям.
  При сравнении повторов используется нормализованное тело.

Проверены локальные вызовы без TLS. Оба порта привязаны к 127.0.0.1.

## Тайм-ауты сервера

Пул соединений ждёт до 2 секунд, JDBC-запрос — до 3 секунд,
транзакции создания и обновления — до 5 секунд.
gRPC-обработчик проверяет отмену до и после операции.
Отмена RPC не гарантирует отмену уже выполняющегося SQL или откат commit.
Идемпотентность нужна в том числе для этого случая.

Для реального размещения потребуются авторизация, TLS, миграции схемы,
наблюдаемость и отдельная проверка под целевой нагрузкой.
